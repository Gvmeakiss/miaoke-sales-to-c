# 销售 ToC 核对项目

本项目用于核对 2026-01-01 至 2026-06-30 的销售 ToC 数据链：

`旺店通订单 → 惠策对账明细 → 惠策店铺汇总 → OMS 月结Y001标准结算子集 → SAP 标准发票（2C）`

上述为业务数据获取与处理路径；正式审计底稿总览以SAP收入确认端为起点，按 `SAP开票 → OMS月结 → 惠策账单汇总 → 惠策账单明细 → 旺店通订单` 向业务源头逐层穿透。

当前工作区按“原始输入、正式交付、可复现代码、可复算数据、过程归档”五层管理。历史 V2/V3/V4/V4.1、修复版及demo不再作为正式版本使用；本轮检查日志和中间结果统一归档至`archive/20260804/`。

## 2. 数据范围与来源

- 账单及财务核对期间：2026-01-01 至 2026-06-30，含首尾。
- 旺店通正式匹配期间：2026-01-01 至 2026-06-30。2025年12月订单仅用于Cut-off敏感性分析，不纳入正式匹配结果。
- 旺店通：`input/旺店通订单清单/`，订单表头及商品明细。
- 惠策明细：`input/惠策系统对账单清单/`，共 16 份订单级对账明细；其中`历史账期对账结果明细6月-3.xlsx`为客户补充的结账延迟遗漏账单。
- 惠策汇总：`input/惠策系统对账单汇总/`，共 19 份店铺级月度汇总；其中`对账店铺汇总6月-3.xlsx`为客户补充的遗漏记录。
- OMS：`input/OMS 系统日结月结查询记录：25年12月到26年6月2C单据.sql`。
- 结算中心发货对账明细：`input/对账明细（to oms 月结）/`。程序自动识别`发货对账明细YYYY.MM.xlsx`、同月分片及跨月导出。所有文件均使用原始字段“账期结束日期”归属结算月，不以文件名或账期开始月代替。6月末D-1/D-2记录即使在7月初完成对账仍纳入；账期结束日在2025年12月或2026年7月的记录作为审计期外数据排除。
- OMS日/月结事务码：`input/日结月结事务码.xlsx`。程序按“业务类型/事务码”识别：月结为`Z008、Y001、Y003、Y004、Z007、Y011`；日结为`Y005、Y006、Y002、Z001-Z006、Y051、Z011-Z051、Y052、Y021`。OMS原字段`结算类型(cycle_type)`不作为日/月结分类依据。
- SAP标准发票（2C）专项核对继续使用月结中的`Y001`标准结算子集：当前实际数据中，SAP共同键仅在Y001出现；其余月结事务码作为月结全量分类保留，不混入标准发票逐笔匹配。
- SAP：`input/发票清单：26.01.01-26.06.30/`。
- 旺店通店铺主数据：`input/旺店通内店铺id与店铺名称映射.csv`，用于店铺 ID—OMS 客户优先映射。

原始资料不随核对过程修改。当前惠策明细和汇总导出均没有物料、SKU或商品数量字段。

## 3. 核对逻辑

### 3.1 旺店通订单—惠策明细

- 核对基表：合并后的惠策账单清单。现有月度清单与`历史账期对账结果明细6月-3.xlsx`按对账流水号Append去重，现有月度记录优先，补充文件仅追加唯一遗漏记录。
- 补充文件不执行账期或日期范围过滤，按2026年6月补充导出批次参与所有惠策相关匹配；不再单独执行惠策6月28/29日Cut-off日期抽样。
- 正式订单候选池：仅使用2026-01-01至2026-06-30的旺店通订单，同时参考有效交易/付款日期及发货日期。
- Cut-off敏感性分析使用现有旺店通订单池中的2025年12月订单，按与正式范围相同的订单号及金额逻辑补充测算，不写入或覆盖正式订单候选池。
- 强键：`旺店通原始单号 = 惠策平台订单号`。
- 二级辅助证据：强键未命中时，如同一旺店通内部订单号下至少存在一笔已命中惠策的平台订单号，且待解释平台订单的旺店通分摊金额为零，则分类为“同内部订单零金额附属单”。该规则只解释订单/数量覆盖，不将零金额记录计入金额匹配。
- 分类原则：平台订单号精确匹配及同内部订单零金额附属单分别列示，其他订单按核对分类展示。
- 映射粒度：一行一个平台订单号，同时保留旺店通内部订单号集合、惠策对账流水号集合、店铺及月份。
- 金额口径：旺店通平台订单分摊金额 `allocated_total` 与惠策实际实收净额比较；惠策实际实收净额=收款金额（正实收）-退款金额（负实收）。旺店通金额仅作为订单—账单桥接金额，不作为最终收入确认金额。
- 正式范围完整平台订单并集为 5,898,788 行，保存在 `reconciliation/results/order_bill_recon.csv`；正式Excel不再嵌入该过程明细页，仅在汇总页列示分类金额。

### 3.2 惠策店铺汇总—OMS 月结

- 惠策没有物料字段，按月份 + 惠策店铺/OMS客户映射核对金额。
- 店铺映射优先使用旺店通店铺 ID—名称主数据，并以 OMS 客户编码核验；主数据未覆盖的店铺继续使用现有名称/交易匹配逻辑兜底。
- 客户另行确认的 `快团团供应商→817722`、`快团-妙可蓝多奶酪星球→813210` 作为更高优先级的客户确认映射；OMS SQL 中无对应交易的组合按账单单边记录列示。
- 惠策店铺汇总实际结算金额与OMS `share_amount` 结算金额为主口径。
- 同一客户跨月累计仅解释结算时点，不替代逐月匹配。
- 不执行“OMS未开票池—惠策”核对。

### 3.3 数量链

- Step 1：发货对账明细仅纳入`对账状态=对账成功`，以`实际数量`与OMS月结Y001的`item_num`按结算月份+店铺/客户编码+货品/商品编码核对；金额同步使用`收款金额`与`share_amount`核对。
- 客户确认共同键金额差异主要由跨期结算导致。底稿保留发货对账原共同键金额，并对具有跨期业务月份/原账期证据的共同键单列“跨期结算调整金额”；调整金额=`OMS月结共同键金额-发货对账原共同键金额`。调整不覆盖原始记录、不调整任何单边金额，逐条依据在`4.对账结果-OMS月结明细`中保留。
- Step 2：OMS 与 SAP 按销售单号 + 物料编码 + 销售单位核对双方原生数量。
- 正式底稿不进行旺店通、惠策、OMS、SAP四方数量直接比较，数量差异按“发货对账—OMS月结”和“OMS月结—SAP”两段业务流分别列示；订单—账单仍作为补充稽核展示。
- `1.全局口径与总览` 下方新增“已验证业务流及匹配比率”和“业务流信息（供财务人员理解）”：正式2026年1—6月核对与5月发货链补充验证分区列示，避免将局部验证比例误读为全期间结论。
- 已验证业务链补充结果保存在 `reconciliation/results/verified_business_flow_metrics.json`，列示旺店通—发货对账明细、发货对账明细—惠策、结算中心核销成功—OMS月结Y001，以及慧策收入汇总—SAP差异过账店铺月支线的实际值核对控制数。

### 3.4 OMS 月结—SAP

- 强键：OMS销售单号 + 物料编码 + 销售单位。
- 对客户确认的SAP错录销售单号，在钩稽层建立“原录入单号→正确OMS单号”显式映射；原始SAP清单不修改，更正记录、受影响发票、数量及金额在`2.OMS月结-SAP汇总`保留审计轨迹。
- 同时比较数量和含税金额。
- 一致键用于双向补充客户、月份、发票号等字段；双方单边记录完整保留。

## 6. 重跑方式

### 6.1 使用现有数据库刷新正式结果

```bash
python3 reconciliation/reload_wdt_orders.py
python3 reconciliation/reconcile_sales_flow.py --output-dir reconciliation/results
python3 reconciliation/analyze_wdt_cutoff_sensitivity.py
```

生成 Excel 时需使用 Codex 工作区提供的Python、Node.js与`@oai/artifact-tool`依赖。构建脚本会先扫描原始发货对账文件、刷新`settlement_oms_workpaper.json`，再生成底稿；临时依赖链接完成后自动清理：

```bash
WORKSPACE_PYTHON='<workspace-python>' \
WORKSPACE_NODE='<workspace-node>' \
WORKSPACE_NODE_MODULES='<workspace-node_modules>' \
  reconciliation/build_workpaper.sh
```

新增发货对账文件放入`input/对账明细（to oms 月结）/`后，无需修改月份清单即可直接运行上述命令。刷新程序执行以下控制：

1. 单月文件及其分片按文件名月份纳入；`2026.01-2026.02`等既有多月文件按“账期开始日期”拆分；`2026-06 07`跨月导出按“账期结束日期”拆分并执行2026-06-30审计截止控制。
2. 发货对账仅纳入`对账状态=对账成功`，金额取`收款金额`，数量取`实际数量`；OMS仅纳入Y001，金额取`分摊金额`，数量取`数量`。跨期结算共同键在原始金额之外另列桥接调整及调整后金额，单边记录不作调整。
3. 相同文件SHA-256仅纳入一次；跨文件完全相同业务行仅保留首次记录，同一文件内部重复行不擅自删除。
4. 缺少任一侧资料的月份标记“待获取”，不以0参与合计或匹配率；跨期补充文件在汇总及明细中保留来源和期间标识。

仅检查明日文件是否已被识别、但不读取大文件时，可运行：

```bash
'<workspace-python>' reconciliation/refresh_settlement_oms_workpaper.py --inventory-only
```

2. Excel公式错误扫描是否为0。
3. 10个正式工作表页面预览是否完整、无截断；订单—惠策全量过程明细页、月度全流程分析页及解释性规则页不纳入正式交付工作簿。
4. XLSX压缩结构检查是否通过。

## 7. 维护原则

- `input/`、正式底稿及当前数据库不得作为临时目录使用。
- 新测试统一写入 `reconciliation/intermediate/`，验证后可整体删除。
- 不再新增 V2/V3/V4 等并行版本目录；正式结果直接覆盖 `reconciliation/results/` 和正式底稿。
- 需保留历史过程资料时，在`archive/YYYYMMDD/`建立独立只读归档，不与正式交付目录混放，也不覆盖既有归档。
